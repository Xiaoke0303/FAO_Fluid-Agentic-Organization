# Harness 工程化体系架构（FAO 修正版）

> 基于 FAO（Fluid Agentic Organization）框架修正：规则是必需的，但规则不能替代责任。

---

## 修正核心：三条硬约束

| 约束 | 原图问题 | FAO 修正 |
|------|---------|---------|
| **AI 审查不能终审** | AI 审查 AI 产出，审查者悬空 | AI 审查仅为初筛，人类抽样复核才能终审 |
| **反馈回路必须有出口** | 异常信号在 Agent 闭环内空转 | 异常/越界/冲突信号自动升级人类 |
| **规则不能自我改写** | 规则注入 + 反馈回路暗示 Agent 可更新规则 | 规则变更必须经过人类审批锚点 |

---

## 全景架构：四域 + 一贯穿层

### 01 上下文与知识工程（CONTEXT & KNOWLEDGE）

**原图内容：**
- Agent 记忆：项目规则与约定
- 结构化文档：需求/设计/规则
- 代码决策记录：ADR 架构决策记录
- 知识图谱：业务领域与技术知识

**FAO 修正：**

```
Agent 记忆：项目规则与约定
  └── [人类锚点] 规则变更需人审批准

结构化文档：需求/设计/规则
  └── [人类锚点] 需求签字确认

代码决策记录：ADR 架构决策记录
  └── 🚪 [人类强制确认门] ADR 写完后必须人类批准才能生效

知识图谱：业务领域与技术知识
  └── [人类锚点] 知识注入需人类审核来源与准确性
```

> **关键修正**：ADR 不是"记录了就完了"，而是"记录后必须有人类批准才能生效"。否则 Agent 可能基于未经批准的 ADR 做出错误架构决策。

---

### 02 约束与规范（CONSTRAINTS & STANDARDS）

**原图内容：**
- 需求规范：模板与验收标准
- 设计规范：约束规则/边界
- 测试规范：测试策略/测试标准
- 代码规范：编码规范/代码风格
- 变更规范：变更管理/最佳实践

**FAO 修正：**

| 规范类型 | 原图定位 | FAO 修正 |
|---------|---------|---------|
| 需求规范 | 模板与验收标准 | 验收标准由**人类制定**，Agent 不可自行修改 |
| 设计规范 | 约束规则/边界 | 边界变更需**人类审批**，Agent 只能在边界内活动 |
| 测试规范 | 测试策略/标准 | 测试通过 ≠ 业务验证通过，后者需**人类确认** |
| 代码规范 | 编码规范/风格 | 可由 Agent 执行检查，但**例外放行需人类签字** |
| 变更规范 | 变更管理/最佳实践 | 规则本身变更需走**独立审批流**，不能由反馈回路自动更新 |

> **关键修正**：规范不是"设定好就交给 Agent 自治维护"，而是"人类定规则、Agent 在规则内执行、规则变更需人类重新确认"。

### 04 工具与沙箱（TOOLS & SANDBOX）

**原图内容：**
- 外部工具：API / 第三方服务
- 自动化操作：CI/CD / Git
- 模拟控制：白名单/规则限制
- AI 审查/AI 验证

**FAO 修正：**

| 组件 | 原图定位 | FAO 修正 |
|------|---------|---------|
| 外部工具 API | API / 第三方服务 | **权限最小化**：每个 Agent 只能调用其任务所需的最小工具集 |
| 自动化操作 | CI/CD / Git | 部署脚本可自动化，但**生产发布需人类确认** |
| 模拟控制 | 白名单/规则限制 | ✅ 正确方向：默认拒绝，显式授权 |
| AI 审查/验证 | AI 自动执行 | 增加"人类抽样复核"节点 |

## 核心目标修正

| 维度 | 原图 | FAO 修正版 |
|------|------|-----------|
| 核心目标 | 驱动 AI 持续输出高品质、**可规模化**的交付成果 | 驱动人机协同持续输出高品质、**可规模化且可验证**的有效价值 |
| 隐含假设 | 规模化 = 更多产出 | 规模化 = 更多**有效**产出，且每个产出都可追溯责任 |
| 质量定义 | 代码/测试通过 | 代码/测试通过 + 业务价值确认 + 责任锚定 |

---

## 与原图的最大区别

| 维度 | 原图 | FAO 修正版 |
|------|------|-----------|
| 审查机制 | AI 审查 AI（终审） | AI 审查 → 人类复核（终审） |
| 反馈回路 | Agent 自治闭环 | 自治 + 异常升级人类 + 规则变更需人批 |
| 规则来源 | 注入后即执行 | 注入后需人类确认，变更需独立审批 |
| 沙箱边界 | 白名单限制 | 白名单 + 越界阻断 + 审计升级 |
| 目标导向 | 可规模化交付 | 可规模化交付**有效价值** |
| 责任结构 | 隐式分散 | 显式锚定（每个关键节点有人类签字） |

## 最小落地建议

如果要落地这个 FAO 修正版 Harness 框架，建议分三步：

### Step 1：加一扇门（最低成本）
在现有流水线中，选择**最关键的节点**加第一个"人类强制确认门"。建议选：
- **ADR 批准门**：架构决策记录写完后，必须指定人类架构师批准才能进入编码

### Step 2：加一个复核（中等成本）
在 AI 审查后加"人类抽样复核"：
- 不是每份代码都审，而是按风险等级抽样（高危 100% 复核，中危 30% 复核，低危 10% 复核）

### Step 3：加一个出口（完整闭环）
在反馈回路中加"异常升级通道"：
- 定义 5 类必须升级人类的异常信号
- 建立升级后的"人类裁决 → 规则更新建议 → 人类审批 → 生效"的完整链路

## 使用建议

1. **展示时用**：强调"蓝色是 Agent 域，红色是人类锚点，红色不能省略"
2. **落地时用**：从 Step 1 开始，不要试图一次性改造整个流水线
3. **优化时用**：监控两个核心指标——"AI 审查漏检率"和"异常升级响应时间"
